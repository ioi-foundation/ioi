## 1. Executive decision

IOI does not need another broad architecture expansion before it proves the
architecture already described. It needs one product that compresses the
substrate into an obvious user outcome and mechanically exercises the claims
that distinguish the substrate.

The first undeniable proof is:

> **An OutcomeRoom-backed bounded software-change institution that admits
> humans, first-party workers, and one untrusted local agent; converts an issue
> into a verified change through a durable GoalRun; revalidates authority at
> the exact consequential-effect boundary; preserves private institutional
> learning across provider replacement; and leaves independently verifiable
> lifecycle, authority, effect, and outcome evidence.**

This proof is intentionally narrower than the target architecture. It uses one
node, one hosted room-admission domain, one logical System, local settlement,
and a sandboxed repository. It does not require multi-node continuity, public
consensus, a sovereign L1, a native asset, live payments, physical actuation,
or federated room admission.

That narrow profile is not a retreat from the Internet of Intelligence thesis.
It is the minimum product-shaped experiment that proves the following stack is
coherent:

```text
familiar product intake
  -> semantic objects and actions
  -> bounded System genesis
  -> OutcomeRoom shared frontier
  -> durable GoalRun pursuit
  -> admitted workers, tools, data, and local-agent proposals
  -> verification and course correction
  -> commit-time consequential-effect authorization
  -> Agentgres-owned state and receipts
  -> inspectable outcome, replay, recovery, upgrade, and exit
```

The guide then expands by evidence, not by noun count:

```text
minimum local proof
  -> product compression and external usability
  -> production integration
  -> enterprise learning and provider exit
  -> two-sovereign positive-surplus cooperation
  -> embodied sim-to-live assurance
  -> demand-gated public network services
```

## 3. Terminal proof profile

### 3.1 Selected deployment profile

| Dimension | Frozen proof choice |
| --- | --- |
| Product scenario | Governed software-change institution over one sandboxed repository |
| Logical identity | One bounded System; the durable OutcomeRoom is its flagship bounded-DAS instance |
| Deployment | One node, one active writer, one failure domain for the minimum proof |
| Room admission | Hosted admission by one named governed domain |
| Ordering/finality | Local operational finality; no public consensus dependency |
| Contributors | One human sponsor, first-party worker routes, one room-scoped untrusted local agent |
| Local-agent posture | Authenticated pairing, proposal-only/read-only preflight, one bounded claim, no ambient room or repository authority |
| Work | One issue, one shared frontier, at least two admitted attempts, one named verifier path, one accepted `OutcomeDelta` |
| Consequential effect | Merge the exact verified commit into a protected sandbox branch; an optional sandbox deployment remains a separately authorized effect |
| Authority | Embedded product sign-in; externally owned product-session/origin binding; passkey step-up for the merge; exact JCS-hashed authority request/review; context-bound portable `AuthorityGrantEnvelope` v3 successor; daemon revalidation at invocation and commit |
| Data | Private repository and private evaluation containing a unique canary |
| Model routes | At least two substitutable eligible provider or local routes |
| Truth and evidence | Agentgres-owned admitted state, lifecycle facts, effect records, checkpoints, and offline-verifiable export |
| Billing | Measured internal cost only; no live processor, payout, escrow, or token dependency |
| Cooperation | Same-domain hosted room for the terminal proof; cross-sovereign cooperation is a later lane |
| Embodiment | None in the terminal proof |
| Public settlement | None; local proof cannot depend on a public chain |

### 3.2 End-to-end journey

The terminal demonstration must be executable by a person who did not build
the system:

1. Continue with an ordinary identity provider or passkey without wallet,
   chain, key, or grant terminology.
2. Choose **Create software change room** from a template.
3. Connect or create the sandbox repository and select the protected target
   branch.
4. Review a compact purpose, constitution, ontology/action set, data posture,
   verifier path, budget, and authority preview.
5. Validate and simulate the package; every blocked dependency names the exact
   owner, missing evidence, and remediation.
6. Perform governed genesis and receive a stable System and OutcomeRoom
   identity.
7. Submit an issue; the room opens a shared frontier and admits a durable
   GoalRun from one immutable `GoalRunProfile`.
8. Connect one external local agent through an expiring, origin-bound,
   single-use pairing flow.
9. Admit that agent only as a proposal-only room guest and award one bounded
   claim.
10. Let first-party and local contributors publish positive, negative, or
    inconclusive attempts with exact composition, artifacts, and evidence.
11. Reproduce the best candidate under the named verifier path; retain failed
    attempts and challenges.
12. Replace an execution Session and restart the daemon while the GoalRun
    remains durable and reconstructable.
13. Present the exact accepted commit, tests, provenance, budget, destinations,
    and risk in an embedded authority review.
14. Use a platform passkey for local user verification; authentication alone
    must never authorize the merge.
15. Revalidate the exact grant, current policy, writer fence, information-flow
    labels, target commit, branch head, and effect hash immediately before the
    merge is committed.
16. Merge once or fail closed. Retry, stale-head, revoked-grant, substituted
    commit, and deposed-writer paths must produce zero duplicate or unauthorized
    repository effects.
17. Inspect the room frontier, GoalRun decisions, attempts, verification,
    authority, effect, and accepted outcome through Systems, Work, Governance,
    and Provenance projections.
18. Export a portable proof bundle and verify it offline without producer
    database access.
19. Disable the primary model provider and continue above the deployment's
    frozen Model Independence threshold using institution-controlled state.
20. Exercise lost-device recovery, revoke the old factor and affected leases,
    and prove that recovery does not rewrite earlier evidence or widen power.
21. Upgrade, recall, archive, restore, and retire the package/System through
    governed lifecycle paths.

## 4. Reusable independent goal-pass protocol

Every implementation unit is an independently reviewable **goal pass**. A pass may be
research, contract work, integration, product work, adversarial verification,
or a deployment trial, but it follows the same protocol.

### 4.1 Goal-pass record

Each pass records:

```text
pass_id
pass_kind: discovery | contract | integration | product | adversarial | field
objective: one falsifiable result
hypothesis_or_contract
selected_profile
baseline_and_date
canon_owners
inputs_and_exact_versions
dependencies
in_scope
out_of_scope
implementation_surfaces
applicable_pg_ids
positive_proof
adversarial_or_fault_proof
user_journey_if_visible
metrics_and_thresholds_frozen_before_execution
evidence_index
migration_and_compatibility
remaining_nonclaims
canon_feedback_refs
rollback_or_stop_rule
disposition
```

This is planning syntax, not a new canonical envelope.

### 4.2 Pass lifecycle

```text
proposed
  -> scoped
  -> admitted
  -> executing
  -> evidence_ready
  -> verified
  -> absorbed | retained_as_reference | rejected | superseded
```

`blocked` may annotate any nonterminal state but must name the missing owner
decision, dependency, authority, environment, evidence, or user input.

### 4.3 Admission rules

A pass starts only when:

1. its objective can be disproved;
2. its deployment profile and nonclaims are explicit;
3. its owner documents and current implementation status have been read;
4. its dependencies are either verified or intentionally simulated;
5. its metrics are frozen before results are observed;
6. it identifies all consequential effects and the final invokers;
7. it maps relevant `PG-*` IDs without changing their authoritative
   dispositions;
8. it declares how negative and inconclusive results will be retained.

### 4.4 Completion rules

A pass is `verified` only when:

- the positive path works through the real owner boundaries selected by the
  profile;
- at least one plausible bypass, substitution, retry, stale-state, and
  unavailable-dependency path has been tested where relevant;
- persistent evidence survives restart and can be reconstructed;
- product-visible empty, degraded, denied, and recovery states are honest;
- migration and mixed-version behavior are stated;
- the evidence is linked from the pass record;
- remaining nonclaims are narrower than the completed claim.

A pass fails when its frozen threshold is missed. The disposition may be
`rejected`, `superseded`, or a new pass may be proposed with a changed
hypothesis. Results must not be relabeled after observation merely to declare
success.

### 4.5 Independent discovery loop

Competitor, standards, research, and user-observation work uses the same pass
shape:

```text
observe a real job or mechanism
  -> state the IOI gap as a measurable hypothesis
  -> identify the existing IOI owner
  -> prototype the smallest source-neutral adaptation
  -> compare against the current IOI baseline
  -> adopt, adapt, reject, or defer
  -> feed an owner-level issue only when evidence reveals an invariant gap
```

Vendor nouns, screenshots, marketing taxonomies, and successful demos are
evidence inputs. They never become canonical ownership by resemblance.

### 7.2 `L0` — Minimum contract and walking-skeleton proof

Objective: materialize one real OutcomeRoom bounded System and carry one
software-change outcome from package through genesis, admitted shared state,
result, acceptance, and retirement without parallel truth.

Independent passes:

- `L0-01` register only the pulled package, genesis, constitution,
  OutcomeRoom-child, GoalRun, generic result, and lifecycle contracts;
- `L0-02` generate Rust/TypeScript projections and positive/adversarial
  fixtures from the registry;
- `L0-03` implement source-neutral `init`, `validate`, `plan`, and `simulate`
  over one compact package representation;
- `L0-04` perform governed one-node genesis and mint stable System identity;
- `L0-05` admit room frontier, claim, attempt, finding, challenge, result, and
  accepted delta through their real owners;
- `L0-06` emit Agentgres-owned state, checkpoint, and offline proof export;
- `L0-07` upgrade, recall, archive, restore, and retire the instance.

Required proof:

- two independently created instances of the same package receive different
  stable System identities while retaining the same package root;
- rejected or malformed room objects never enter admitted shared state;
- crash/restart reconstructs the same accepted heads and proof root;
- the source package, visual projection, daemon input, and stored identity do
  not diverge semantically;
- no public chain, marketplace, or Wallet console is required for local
  correctness.

Metrics:

- 100% generated-projection parity over registered terminal contracts;
- zero accepted negative fixtures;
- zero client-minted System identities;
- 100% offline verification of exported terminal receipts and checkpoints.

### 7.4 `GR` — Durable GoalRun and orchestration proof

Objective: prove that a goal is durable pursuit state rather than a chat,
process, Session, harness invocation, or mutable controller loop.

Independent passes:

- `GR-01` freeze immutable `GoalRunProfile` resolution, admitted overrides,
  orchestration constraints, verifier paths, and tool/capability requirements;
- `GR-02` bind GoalRun, GoalGroundingLoop, WorkRun, HarnessInvocation,
  ContextCell, and external handles to the shared lifecycle mechanism;
- `GR-03` replace Sessions, workers, harnesses, and model routes without
  replacing GoalRun identity or losing admitted state;
- `GR-04` preserve pursue, verify, course-correct, cancellation, compensation,
  archive, and continuation history as append-only facts;
- `GR-05` prove deterministic reconstruction and typed mixed-version refusal.

Falsifiable gate:

- one GoalRun survives at least three execution-Session replacements, one
  daemon crash, one provider failure, one worker timeout, one verifier
  rejection, and one course correction;
- retries never duplicate an admitted effect;
- cancellation leaves every child terminal, fenced, or explicitly ambiguous
  with a reconciliation obligation;
- a replay reconstructs the exact GoalRun head, child index, decisions,
  negative attempts, and receipt lineage.

Metrics:

- zero lost accepted transitions across the fault suite;
- zero duplicate consequential effects;
- exact replay-root equality in every supported restore;
- 100% typed refusal for unsupported legal-table or schema versions.

### 7.5 `AUTH` — Estate-wide consequential-effect authorization

Objective: ensure that every consequential effect is authorized against the
exact current effect at the final invoker, not merely approved during an
earlier plan or copied from a receipt field.

Independent passes:

- `AUTH-01` enumerate wallet, Agentgres, connector, storage, deployment,
  settlement, browser/computer-use, and actuator effectors and their final
  invokers;
- `AUTH-02` mount portable grant verification, revocation, information-flow,
  budget, destination, and owner-derived writer-fence checks at each selected
  production PEP;
- `AUTH-03` register and issue the context-bound portable
  `AuthorityGrantEnvelope` v3 successor over the exact JCS authority-request
  body, authenticated principal, externally owned product session, origin,
  factor/guardian review posture, resources, destination, budget, policy, risk,
  expiry, holder, and audience;
- `AUTH-04` add commit-time authorization over that exact context plus
  content/effect hash, branch or object head, writer epoch, and revocation
  epoch;
- `AUTH-05` prove no check/use gap across queue delay, retry, redirect,
  fallback, provider substitution, stale projection, and concurrent mutation;
- `AUTH-06` emit denial and effect receipts only after the correct durable
  boundary.

Falsifiable gate:

- foreign signer, wrong holder, wrong audience, widened scope, stale key,
  revoked grant, stale branch head, substituted content, changed destination,
  budget overrun, restrictive-parent label, deposed writer, and retry replay
  each cause zero final-invoker calls;
- a valid exact grant produces one and only one bound effect;
- an inventory-to-route test proves there is no unclassified consequential
  production route in the selected estate.

Metric:

- `unauthorized_final_invoker_calls = 0` across the complete adversarial matrix.

The commit-time-authorization research linked below is a discovery input. IOI
must validate its property through its own owner contracts and tests rather
than importing paper terminology as canon.

### 7.6 `PROOF` — Compositional real-world assurance

Objective: make assurance compose honestly across contract validity, identity,
authority, information flow, execution, evidence, verification, acceptance,
attestation, dispute, and settlement, including useful scope-bounded reliance
on external-world assertions, instead of allowing one strong component or
badge to overstate the whole.

Independent passes:

- `PROOF-01` define each product claim and external fact class as a typed
  predicate over exact evidence, applicability, consequence scope, validity,
  and named enforcement boundaries;
- `PROOF-02` implement the deterministic `OracleEvidenceProfile` evaluator over
  assertions, evidence/dependency graph, verifier results, freshness,
  uncertainty, contradiction, and policy, emitting only
  `admitted_for_scope`, `held_unknown`, `rejected`, or `escalated`;
- `PROOF-03` implement independence/correlation evaluation so aliases, workers,
  models, nodes, or feeds under one hidden principal/dependency do not count as
  independent and missing affiliation evidence never passes;
- `PROOF-04` admit evaluator decisions and matching domain assertions through
  distinct `OracleEvidenceAdmissionReceipt` and
  `OntologyAssertionAdmissionReceipt` exact-head CAS chains, then revalidate
  the active oracle receipt/head, expiry, profile/source/verifier revocation
  posture, applicability, and consequence scope at every selected
  consequential effect;
- `PROOF-05` inject late contradiction, source/verifier revocation, profile
  replacement, challenge, expiry, reversal, compensation, and reconciliation
  while preserving immutable history;
- `PROOF-06` prove consensus non-equivalence by finalizing both supported and
  false oracle inputs without allowing finality, acceptance, adjudication, or
  settlement to relabel either as external truth;
- `PROOF-07` bind daemon build, policy-engine version, runtime posture and
  selected assurance-meet inputs, then test forged, unavailable, stale,
  self-issued, circular, downgraded, and mutually inconsistent evidence;
- `PROOF-08` render the exact stage—attested, evidenced, verified, accepted,
  adjudicated, or settled—without a global “verified agent/system” badge;
- `PROOF-09` exercise jurisdiction, retention, erasure, incident, and
  accountable-issuer inputs for any selected regulated profile.

Falsifiable gate:

- weakening or removing any required component can only narrow or invalidate
  the composed claim;
- unknown evidence never silently becomes safe, verified, compliant, or
  settled;
- correlated multiplicity never becomes independence, forked oracle-decision
  heads never both become current, and expired/revoked decisions reach zero
  consequential invokers;
- an admitted assertion remains a defeasible, time- and consequence-scoped
  operational determination; a receipt proves its decision boundary and later
  disposition never automatically increases factual accuracy;
- an unattested trusted-operator deployment remains usable only under its
  declared narrower posture;
- every claim can be independently recomputed from its declared immutable
  inputs;
- generated policy projection remains `not_determined` for legal conformity
  unless a separately accountable issuer makes a scoped claim.

Metrics:

- zero assurance upgrades from missing or weaker evidence;
- 100% deterministic recomputation for the terminal claim set;
- 100% product copy parity with the computed assurance stage.

### 7.7 `WAL` — Embedded sign-in-to-effect and recovery

Objective: make wallet.network's authority useful through familiar product
authentication and platform authenticators while preserving the separation
between sign-in, approval, authority issuance, effect admission, and recovery.

Independent passes:

- `WAL-01` ordinary federated/passkey sign-in and native identity link without
  crypto terminology while the calling product retains its own session
  lifecycle;
- `WAL-02` provider-neutral AuthFactor and explicit GuardianSurface enrollment
  plus exact JCS-hashed authority review bound to principal, product session,
  origin, subject, resources/destination, budget, policy, risk, expiry, and
  result;
- `WAL-03` WebAuthn registration/authentication/step-up verification over
  challenge, ceremony context, type, RP hash, origin/cross-origin posture,
  credential owner/user handle, signature, required UP/UV, and BE/BS signals;
- `WAL-04` context-bound portable `AuthorityGrantEnvelope` v3 issuance,
  audience/holder binding, revocation discovery, and final-invoker
  verification;
- `WAL-05` receipt and activity projection inside the originating product;
- `WAL-06` device enrollment/removal, lost-device recovery, guardian or
  organization recovery, key rotation, panic revoke, and bounded outage;
- `WAL-07` self-hosted/deployment-local identity and authority-provider proof.

Falsifiable gate:

- sign-in alone reaches zero consequential invokers;
- biometric samples/templates never leave the authenticator and never appear
  as identity, authority, receipt, or key material;
- the protected merge succeeds only after an exact review and current
  context-bound v3 grant; a green legacy AuthorityReview or v1/v2 grant check
  cannot satisfy the terminal product gate;
- WebAuthn type, challenge, RP, origin, owner, signature, and required-UP/UV
  substitutions fail; counter regression and BE/BS anomalies are policy inputs,
  not universal clone proof;
- recovery revokes or rebinds affected factors and leases without changing
  prior evidence, silently widening power, or making the provider a new
  application truth owner;
- the same authority contract works through embedded web, CLI/headless, and
  self-hosted presentations.

Initial product thresholds:

- at least 90% successful ordinary sign-in and factor enrollment in the
  terminal usability cohort;
- median protected-effect step-up below 15 seconds after review is understood;
- zero stale-device or revoked-factor effects;
- 100% recovery-scenario audit reconstruction.

These thresholds measure the selected product flow; they do not turn
wallet.network into mandatory hosted identity for sovereign deployments.

### 7.8 `ELP` — Enterprise learning boundary and provider exit

Objective: prove that the organization retains its private data, traces,
corrections, evaluations, memory, adapted artifacts, and improvement lineage
and can continue when a model provider is removed.

Independent passes:

- `ELP-01` compile organization/project learning, source-rights, route-rights,
  custody, export, revocation, and provider-trust rules into the admitted
  System and GoalRun snapshots;
- `ELP-02` seed a unique private correction and evaluation canary and deny
  prohibited provider, cross-tenant, training, plaintext, and egress routes
  before invocation;
- `ELP-03` run eligible private improvement with complete source, dataset,
  evaluation, candidate, and promotion lineage;
- `ELP-04` disable Provider A and meet a frozen Model Independence threshold
  through Provider B or a local route using institution-controlled state;
- `ELP-05` export/import the allowed capability package, revoke a source, and
  prove prospective impact propagation plus honest residual exposure.

Falsifiable gate:

- prohibited routes make zero network calls and the canary never reaches an
  unpermitted sink;
- a second tenant and provider-facing request cannot retrieve protected
  material or derivatives;
- provider removal preserves the institution's declared veteran capability
  above the threshold frozen before the test;
- export manifests state both included and intentionally omitted material;
- revocation cannot claim impossible unlearning and cannot permit new affected
  use.

Metrics:

- `protected_canary_egress = 0`;
- `cross_tenant_retrieval = 0`;
- provider-exit quality, latency, and cost each meet the deployment's frozen
  threshold;
- 100% allowed-export lineage and omission verification.

### 7.9 `EXT` — External standards and local-agent admission

Objective: admit useful third-party and user-local agents without giving them
ambient credentials, room-database access, unbounded context, or authority, and
without making MCP, A2A, or another transport the owner of IOI state.

Independent passes:

- `EXT-01` authenticated, expiring, origin-bound, single-use local-agent
  pairing;
- `EXT-02` exact Worker composition, task fit, dependencies, privacy,
  assurance, authority, and evidence declaration;
- `EXT-03` standards-binding profiles that map external tools, resources,
  prompts, tasks, agent identities, and asynchronous handles into existing IOI
  owners;
- `EXT-04` one room-scoped guest, one proposal-only/read-only preflight, one
  bounded claim, one deterministic verifier, and host-only outcome admission;
- `EXT-05` explicit separate promotion to private reusable worker and later
  public marketplace candidate;
- `EXT-06` independent third-party implementation interop test.

Falsifiable gate:

- a third-party local agent completes the bounded claim without an IOI-private
  runtime patch;
- replayed, expired, wrong-origin, substituted-composition, and widened-scope
  pairing attempts fail;
- the guest cannot enumerate room-private state, obtain raw credentials, call
  effectful tools, promote memory, or admit its own result;
- accepted and rejected proposals retain attributable composition, method,
  artifacts, verifier, and outcome lineage;
- disconnect and revoke end future access while preserving permitted evidence
  and portable exit.

Metrics:

- zero ambient-secret exposure;
- zero direct guest effects in the proposal-only profile;
- 100% replay/expiry/origin negative-fixture refusal;
- at least two independently implemented local-agent clients complete the
  published admission path before claiming open ecosystem interoperability.

### 7.10 `COOP` — Positive-surplus two-sovereign cooperation

Objective: prove that two independently governed systems cooperate because
each receives measured complementary value beyond its permitted outside
option, not because federation is presumed desirable.

Reference scenario: a software-maintainer System and an independently governed
security/evaluation System. The maintainer controls source and merge authority;
the evaluator controls a protected test capability and independent
verification. Neither transfers its entire ontology, context, credentials, or
operational truth.

Independent passes:

- `COOP-01` freeze each party's outside option, private valuation method,
  expected cooperation costs, and minimum acceptable surplus;
- `COOP-02` discover only policy-bound room information and negotiate one exact
  collaboration-terms root;
- `COOP-03` perform independent constitutional, privacy, semantic, capability,
  authority, quote, verifier, and terms admission;
- `COOP-04` exchange signed, replay-safe AIIP objects while each domain retains
  local truth;
- `COOP-05` complete one complementary claim, independent verification,
  acceptance, contribution attribution, and local settlement or nonmonetary
  benefit record;
- `COOP-06` reject one negative-surplus offer and prove that refusal grants no
  context, work, authority, contribution eligibility, or penalty;
- `COOP-07` exit and export the allowed participant state without continued
  room-database trust.

Falsifiable gate:

- each party's ex-ante accepted terms and ex-post measured utility exceed its
  frozen permitted outside option after execution, coordination,
  verification, disclosure, IP, counterparty, dispute, settlement, switching,
  and dependency costs;
- the result would not have been available at the same quality/cost from
  either permitted local alternative;
- discovery and terms negotiation alone confer no membership or authority;
- replay, substitution, semantic ambiguity, terms-root mismatch, and exit do
  not corrupt either local domain;
- the negative-surplus control case refuses cooperation safely.

Metrics:

- positive measured surplus for every required party;
- one safe negative-surplus refusal;
- zero unauthorized cross-domain data or authority transfer;
- portable proof agreement between independent verifiers;
- local operation remains available when the peer or public settlement is
  unavailable.

Connectivity, packet exchange, total traffic, number of agents, and a shared
leaderboard do not count as cooperation value.

### 7.11 `EMB` — Embodied native runtime and sim-to-live promotion

Objective: prove that the same bounded-system substrate can compile, admit,
coordinate, and assure physical work without making a partner robotics runtime,
remote GoalRun, model, or network path the local control or safety owner.

Independent passes:

- `EMB-01` compile one native embodied graph across `micro`, `edge`, and `site`
  strata with exact component, stream, timing, resource-group, world, ODD,
  safety, and controller bindings;
- `EMB-02` run deterministic simulation and SIL with injected stream, timing,
  world-model, resource-conflict, partition, and controller faults;
- `EMB-03` run HIL and shadow mode with the independent
  `LocalControlSupervisor` retaining final veto;
- `EMB-04` promote through limited-live canary only after exact evidence and
  authority revalidation;
- `EMB-05` prove safe stop, e-stop, restart-unarmed, standby takeover,
  rollback, recall, operator handoff, and ambiguous-effect reconciliation;
- `EMB-06` repeat the contract on at least one lightweight controller profile
  and one multi-unit coordination profile before making general runtime
  claims.

Falsifiable gate:

- denied or stale physical intent reaches zero actuator calls;
- every accepted call uses the exact fenced controller, resource group,
  world/ODD state, safety envelope, and authority;
- learned or remote outputs remain proposal-only above deterministic local
  control and safety;
- restart is inactive and unarmed;
- simulation, SIL, HIL, shadow, and limited-live evidence remain linked without
  treating simulation as live proof;
- lower assurance evidence cannot render a higher E-level claim.

Metrics must include the owner-required p50/p99/p999 latency and jitter,
deadlines, queue/backpressure, safe-state time, interventions, violations,
replay fidelity, resource/spacetime conflicts, partition/rejoin, and
promotion/rollback results. No live action begins while any applicable
`PG-5.*` gate remains open.

### 7.12 `PROD` — Production and SRE integration

Objective: move the terminal product from bounded reference mechanisms to
authentic owner integration and known behavior under failure, recovery,
version change, key change, saturation, and operator intervention.

Independent passes:

- `PROD-01` authenticated owner-rooted observations and operation-class
  readiness immediately before real schedulers and effectors;
- `PROD-02` correlated fault campaign across daemon, Agentgres, authority,
  storage, clock, provider, checkpoint, and identity/recovery dependencies;
- `PROD-03` real checkpoint/backup/restore, archive, compaction, and retained
  or lost-suffix reconciliation;
- `PROD-04` signer/verifier key rotation and bounded revocation staleness;
- `PROD-05` mixed-version rollout, rollback, upgrade-required behavior, and
  schema migration;
- `PROD-06` capacity, saturation, queue, backpressure, admission control, and
  load shedding;
- `PROD-07` privacy-safe logs, traces, metrics, alerts, incident evidence, and
  learning-sink canaries;
- `PROD-08` runbooks, on-call ownership, recovery exercises, and a terminal
  soak.

Falsifiable gate:

- every operation class matches its declared fault-matrix decision under
  missing, stale, forged, and unavailable plane observations;
- overload or partial outage narrows availability without widening authority,
  dropping accepted truth, or converting an unknown effect into success;
- restored heads and proof roots match the declared checkpoint or produce an
  explicit loss/divergence record;
- key and schema rollout never create two accepted active writers/signers or
  silently discard consequential fields;
- protected raw content never enters a disallowed telemetry or learning sink;
- an operator can diagnose, contain, restore, and explain the terminal fault
  scenarios from shipped evidence and runbooks.

Initial release thresholds:

- RPO of zero for admitted terminal lifecycle, authority, and receipt heads;
- recovery meets the RTO frozen for the selected deployment before fault
  testing;
- zero authority widening across the correlated fault suite;
- zero silent mixed-version downgrade;
- a 72-hour terminal-profile soak with no unreconciled accepted-state loss,
  duplicate consequential effect, or protected-data egress.

### 7.13 `NET` — L1 and native-asset demand gate

Objective: determine whether shared public IOI network services require a
sovereign L1 and native risk-bearing asset, using observed demand and security
economics rather than architectural enthusiasm.

Independent passes:

- `NET-01` instrument demand for registry, rights, escrow, service bonds,
  verifier/guardian/availability services, disputes, and public commitments;
- `NET-02` operate selected services on a devnet or mature compatible
  settlement environment;
- `NET-03` measure external demand, fee willingness, bonded risk,
  availability/security requirements, performance, governance needs,
  switching costs, and failure behavior;
- `NET-04` freeze and evaluate a security-budget model, validator/guardian
  participation model, demand concentration, attack cost, migration burden,
  and public-capacity requirement;
- `NET-05` produce an owner/ADR decision to remain on compatible settlement,
  extend the trial, or pursue a sovereign network;
- `NET-06` evaluate a native asset only if gas, security bonds, slashing,
  claims, scarce public capacity, or governance require risk-bearing capital.

Falsifiable gate for even considering a sovereign L1:

- at least three unrelated external organizations create recurring paid or
  risk-bearing demand across at least two public service families;
- demand persists for at least six months on the compatible environment rather
  than appearing only in a subsidized launch event;
- modeled sustainable fees and bonded value cover the selected security and
  availability budget with an ex-ante safety margin;
- sovereignty, neutral ordering/security, performance, or governance creates
  measured value greater than migration, operational, liquidity, regulatory,
  and security costs;
- independent operators are willing to provide the required security,
  verification, guardian, availability, relay, or adjudication services;
- the decision remains valid when token-price appreciation is set to zero.

If any gate fails, the correct result is to keep L0 useful and use a compatible
settlement environment. Work Credits remain product accounting and cannot
silently become gas, money, or the native asset. A token per agent, GoalRun,
OutcomeRoom, node, or bounded DAS is out of scope.

## 10. Product discovery and competition loop

Product discovery is continuous but subordinate to owner contracts.

For each material competitor, standard, research result, or user workflow:

1. record the exact observed version/date and primary source;
2. name the user job or mechanism, not the vendor feature name;
3. state the current IOI baseline;
4. propose one measurable adaptation through an existing owner;
5. build a bounded prototype or usability test;
6. compare time, correctness, authority clarity, evidence, portability, and
   recovery;
7. disposition `adopt`, `adapt`, `reject`, or `defer`;
8. link the result to the affected lane and any `CF-*` finding.

The target is not feature parity. IOI should combine:

- ontology-backed object/action composition and operational applications;
- clear visual and code builder convergence;
- durable agent and workflow execution;
- portable identity, authority, evidence, and provider exit;
- sovereign local truth and conditional cross-system cooperation.

If a competitor is easier because it silently centralizes authority, truth,
learning exhaust, or provider dependence, IOI must improve its interaction
design without copying that ownership collapse.

Those findings use stable `CF-*` records in this guide:

```text
finding_id
observed_evidence
affected_owner
current_canon_statement
implementation_or_user_consequence

```

Rules:

1. If evidence changes only implementation status, update
   `canon-to-code-delta.md` and `implementation-matrix.md` after the proof; do
   not rewrite doctrine.
2. If one owner's semantics change, amend that owner first and then update its
   source-map, defaults, vocabulary excerpt, status, and generated references.
3. If ownership or cross-owner invariants change, require an ADR.
4. UX findings do not amend canon unless they expose an owner, identity,
   authority, lifecycle, evidence, or invariants problem.
5. Competitor terminology and this guide's pass IDs never become canonical
   objects automatically.
6. `PG-*` closure is recorded only in the hardening ledger.
7. Product taxonomy changes route through the Hypervisor surface owner and ADR
   0016 rather than this file.
8. Sequence changes route through `execution-horizons.md`.
9. Rejected and inconclusive canon findings remain visible with evidence so the
   same conjecture is not repeatedly rediscovered.
10. A claim may narrow immediately when evidence fails; it may widen only after
    the corresponding owner, implementation, and proof are aligned.

## 14. Completion and stop rules

This guide is complete when:

1. the terminal evidence index is complete;
2. all `required_now` and selected `conditional` production gates are closed in
   their owner ledger;
3. independent users can create and operate the product through the compressed
   journey;
4. the effect, learning, recovery, and proof claims survive their adversarial
   tests;
5. every remaining vertical has an honest `later`, `conditional`, or
   `out_of_scope` disposition rather than a simulated implementation.

Stop and correct course when:

- product comprehension fails despite a functioning substrate;
- an effect path cannot name or guard its final invoker;
- proof depends on trusting the producer whose behavior it claims to verify;
- a GoalRun or accepted outcome cannot survive restart and reconstruction;
- provider exit loses the institution's declared capability or protected
  learning;
- cross-system cooperation produces no positive participant-level surplus;
- embodied promotion requires remote intelligence to become the local safety
  loop;
- public-network economics depend on token appreciation, compulsory local
  settlement, or subsidized internal traffic.

The successful end state is not “all lanes shipped.” It is a small,
independently usable local product with verified boundaries, followed only by
expansions whose measured value justifies their additional complexity.
